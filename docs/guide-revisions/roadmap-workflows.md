# Roadmap: useful requests and accountable decisions (review draft)

**Status:** Draft pending screen verification.

## Submit a request

Explain the problem before proposing a feature. Include the workflow affected, who experiences the problem, the consequence, a concrete example and what a successful change would allow. Distinguish a defect in existing behavior from a proposed improvement and avoid putting passwords or confidential production data in a request.

**Example:** Instead of "Make Traffic better," explain: "When the agreement specifies three credits per week, I cannot tell on Tuesday whether the current week has met the required count. I need a line-level weekly progress view, including aired and outstanding credits."

## Triage and discussion

The [Roadmap board](/roadmap) is a channel for collecting and curating product work, not a guarantee of implementation or delivery date. Administrators should identify duplicate requests, ask for missing context, group related work, and distinguish confirmed needs from possible solutions. Comments should add evidence or a materially different use case rather than simply repeat support.

## Interpret status

Read the current card or request page for its actual status and discussion. Do not infer that a popular proposal is approved or that a proposed change is ready to deploy. When a request becomes implemented, link the relevant release note or tool guide so the original requester can learn what changed.

**Review before publication:** Check actual status names, voting and permission controls against the current Roadmap UI before expanding this into click-by-click instructions.
